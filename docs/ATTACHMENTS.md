# QQ / Web 附件与链接解析

2026-11-01 修复。原先 QQ 的私聊文件地址由 NapCat 返回为 HTTP IP 链接，实际下载时服务端断开，错误发生在请求模型之前。Web 虽然能上传 DOCX，但上游本地配置未启用文件提取；其自带提取只接另一个服务商，且插件原先只保存 `message_str`，附件消息在 PG 中会为空。

现在两端共用 `plugin/attachments.py`，在 AstrBot 构建模型请求前完成下载与解析。没有修改 vendor。NapCat 返回的 `/qqdownloadftnv5` 私聊文件使用 QQ 的 `grouptalk.c2c.qq.com` HTTPS 下载入口，保留原始签名参数。普通 QQ 图片域名优先 HTTPS；下载直接连接、验证 TLS、限制大小和重定向，不关闭证书校验。仍无法下载时可尝试本地原生文件接口，最终给出明确解析失败原因，不能声称已经读过。

## 支持范围

| 内容 | 处理 |
| --- | --- |
| DOCX | 正文、表格文字、页眉页脚、脚注和尾注，本地提取 |
| PDF | 文字层，最多 500 页；加密文件和纯扫描件明确提示 |
| TXT / MD / CSV / TSV / JSON / XML / YAML / 常见代码 | UTF-8、带 BOM 的 UTF-16、GB18030 文本 |
| XLSX | 工作表、单元格和公式；不执行公式 |
| PPTX | 幻灯片和备注文字 |
| HTML | 本地正文，去掉脚本和样式 |
| JPG / PNG / GIF / WebP / BMP | DeepSeek Flash 图片识别，含“作为文件发送”的图片 |
| 公开网页链接、QQ 链接卡片 | 复用现有联网开关、调用次数和网页预算，自动读取最多三个不同链接 |

旧版 DOC / XLS / PPT 明确提示另存为现代 Office 格式；不伪报支持。扫描 PDF 请将所需页以图片发送。视频和语音继续由原有链路处理，本次没有新增转写能力。

单文件最大 32 MB，单条消息最多处理 16 个附件；Office 解压总大小不超过 128 MB。单文件文字最多 64000 本地 Token，每条消息全部材料最多 96000；超限明确标注节选，不假装已读完。图片保留原图给当前聊天模型，同时单独提取最多 4000 输出 Token 的文字/视觉说明，分类 `attachment_vision`，实际 API 用量进入现有统计。历史使用已保存的解析结果，不反复发送全部旧图。

## PG 与记忆

原始 `messages.content` 保留用户文字及附件标识。提取内容、文件路径、类型和失败原因在 `message_attachments` 单独保存；`message_context` 视图提供带材料的对话历史和原文检索，摘要也使用该视图。后续无需重新上传就能继续讨论文件。

模型会看到外部材料边界：文件人物、材料观点与用户本人分开，材料内的指令不能改变人设或权限。每日记忆整理和人设变更证据仍读取用户原话表；不能直接用附件正文确认用户事实。没有改变记忆衰减、每日整理频率或人工人设审批。

缓存位于 `runtime/attachments`，文件按内容哈希保存；同名附件不会互相覆盖。文件内容和凭据均不上传 GitHub。数据库记录随所属消息删除；本地缓存目前保留，尚未增加自动清理策略。

## 验证

- 隔离 PG 测试：文档格式、中文编码、图片文件、HTTPS 重试、私网重定向拒绝、下载大小、同名材料、上下文保存和检索、QQ/Web 归一化。
- 实际 Web：上传 DOCX，模型回答正文代号；上传图片，模型识别图中文字；下一轮不重传仍能回答两份材料内容；链接读取成功，API 返回真实 usage。
- 实际 QQ：重新下载此前失败的两个 DOCX 和一个 JPG，用同一归一化函数提取，并恢复到原有 PG 消息的附件记录中。Web 中此前相同三份材料经字节哈希匹配恢复；没有伪造用户新发言或重新发送 QQ 回复。

验收的技术对话只删除其自身会话；恢复原排期时检查并发真实用户消息，不覆盖用户在测试期间的新计时。没有清空正常聊天、人设或记忆，没有创建数据库备份。
