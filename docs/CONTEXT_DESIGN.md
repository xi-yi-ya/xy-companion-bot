# 上下文审查与实施设计（2026-11-01）

目标顺序：长期交流体验、合理成本、Token 节约。原始聊天和记忆存储不按上下文预算删除；人设审批、每日记忆整理、48 小时衰减、8 天归档及每轮一次随机回忆保持原规则。

## 核实结果与旧限制

当前配置与 `/models`、一次真实 Chat Completions 返回均确认使用 `deepseek-flash`，当前 API 名称 DeepSeek-V4.1-Flash；上下文 1,048,576，最大输出 393,216。官方模型版本为 V4.1-Flash-1017。非思考模式继续使用，适合日常陪伴。证据仅保存在本机 `runtime/qa/model-budget-audit.json`，不含凭据。

来源：[模型与计费](https://api-docs.deepseek.com/quick_start/pricing/)、[Chat API](https://api-docs.deepseek.com/api/create-chat-completion/)、[缓存](https://api-docs.deepseek.com/guides/kv_cache/)、[官方 Tokenizer](https://api-docs.deepseek.com/quick_start/token_usage/)。查询日期为 2026-11-01，价格可变。

旧实现将 UTF-8 字节当 Token；记忆预算 2000、历史 4000。历史 SQL 最多 100 条消息，且遇到一条放不下就终止，可能丢失整段近期对话。框架另有 20 轮裁剪，fallback 128000。没有历史摘要。系统提示每分钟更新时间会扰动缓存前缀。普通记忆长度限 240 字，日整理每批 24000 字节、最多八批，长日或单条长消息会失败。只有手动工具检索使用语义向量，常驻记忆仅中文双字词排序。人设 4000 字符、L1 十条上限。输出 4096；用量虽可从原始响应获取，但插件未保存缓存细分及分类费用。

各类记忆共享 30000 总额，分项上限相加允许略大于总额，按实际候选取舍。相关检索与随机抽取并行去重；小于单条记忆的手动预算会显示带编号的随机节选，可用工具找回全文。日常输出不要求写满 12000；这只是防止深入交流或长任务轻易被 4096 截断。L0 / L1 若超限，保存或批准明确失败，原设定完整保留。

这些预算独立于数据库磁盘容量。数据库保留原文、摘要版本和来源，不把预算当存储期限。官方本地 V4 Tokenizer 用于规划；计费和观测以 API usage 为准，不能把本地计数称为账单精确值。

## 动态策略

按同一人的历史按时间构建完整轮次，避免在轮次中间断开；跨聊天入口的来源与日期可追溯。历史达到 216000 时，逐块将较早部分整理为可增量的结构化连续性摘要，保留至少 168000 的近期完整内容作为滞回窗口。摘要任务只在压力阈值触发，不是每轮摘要，也不替代每日 L2 记忆整理。原文始终可再检索。

24000 / 90000 是观察档位，240000 是正常原文容量；实际内容按需增长。相隔八小时再次开始时，可以后台压缩旧话题，目标保留最近约 16800 原文；第一次回来不会因该后台整理等待，除非已经超过正常窗口。连续深入交流中，一句“嗯”不会触发缩窗。24 万窗口在长聊中保留远多于旧实现的原文，同时与 48 万应急输入上限形成余量；没有直接把 100 万物理上限当作每轮发送目标。

摘要早触发后，正常原文通常在 16.8 万至 21.6 万之间滚动。摘要失败时的应急原文约可到 41.6 万（48 万减工具/安全余量），仍保留原始数据。SDK 在最终组装后计入系统、工具 schema、工具续轮和输出预留，超过模型窗口就停止请求并记录 LocalContextLimit。图片采用保守占位计数，实际视觉与帧格式 Token 仍以 usage 为准。后台摘要有活动状态，会显示托盘忙碌。

摘要必须带真实消息来源；关键引文逐字校验；不把助手推断写成用户事实，不提升为 L0/L1。摘要失败保留旧摘要与原文，不推进覆盖检查点；必要时使用更大的应急原文窗口，禁止悄悄跳过未摘要区间。失败重试从一分钟逐步退避至最多十五分钟，记录错误类型和待重试时间，避免每条聊天反复触发失败任务。达到物理上限时明确失败，不无声删掉正在聊的话题。

系统前缀保持稳定；当前时间、动态召回和随机记忆放在当前轮尾部。缓存按相同前缀复用，不承诺命中率。所有真实模型请求（含工具续轮、摘要、每日整理、设定检查）记录 API 输入/输出、缓存命中/未命中、首 Token/总耗时、结束原因和分类费用。上下文记录原文保留量、摘要覆盖、召回与实际注入、压缩和硬截断；回忆准确率与情绪连续性用有答案的回放集评估，不能把检索相似度当准确率。

### 2026-11-04：修复聊天请求的动态前缀

排查发现，后续添加的可引用消息编号、QQ 待处理申请数、空间运行状态重新进入了开头的系统提示，导致后面的完整历史也不能命中缓存。修复前 24 小时普通聊天 57 次请求合计输入 4,273,143 Token，其中命中 171,648（4.0%）；同一服务主动联系约为 95.6%。这是该次排查快照，不是长期指标。

普通聊天现在按以下顺序构建：

1. 固定 L0/L1、记忆使用规则、工具说明和当前已保存的权限设置。
2. 连续性摘要与近期完整历史，保留原有顺序及长度。
3. 本轮来源、引用编号、待处理申请数、空间状态。它们仍是 `system` 角色提供的运行信息，未降为可执行的用户指令或记忆。
4. 当前用户输入、时间、附件资料与本轮重新召回的记忆（含随机归档）。

本地可选 ComfyUI 扩展同样将最新任务状态放到历史之后，固定能力说明仍在前面；主插件不依赖此扩展。没有缓存模型回复、冻结随机记忆、延迟更新权限，也没有改变人设或截断历史。用户修改人设/权限、摘要更新、工具集变化仍可能使前缀失效，这是正确行为。

实际调用 `deepseek-flash` 的隔离对比：使用真实注入钩子与合成历史，每轮变更运行状态，旧布局输入 7,499 Token，第二/三轮命中 384（5.1%）；新布局输入 7,506 Token，第二/三轮命中 7,168（95.5%）。两组各三次请求，首轮均冷缓存。只保存 API 原始 usage 与耗时到本机 `runtime/qa/cache-prefix-evidence.json`；不写正式聊天、记忆或发送 QQ 消息。这验证了前缀布局，不能代替上线后真实长聊的命中率统计或承诺延迟改善。

回归覆盖 QQ 私聊/Web/群聊的稳定历史前缀、当前引用编号、权限隔离、随机记忆更新及可选扩展任务变化。观察效果应查看修复后单轮 `cache_hit_tokens / input_tokens`，不能期待已有当日累计统计立即翻转。首次请求、长时间闲置后的缓存淘汰，以及前缀内容更新后，仍会出现冷缓存；[官方文档](https://api-docs.deepseek.com/guides/kv_cache/)说明缓存需持久化完整前缀单元，共同前缀可能需要后续请求才能命中，服务也不保证 100% 命中。

上线后只读复查（2026-11-04 00:57，北京时间）：9 轮真实 QQ 私聊共有 727,045 输入 Token，命中 633,856，整体 87.18%；首轮冷缓存 0.63%，随后 8 轮按输入加权命中 98.05%（单轮 96.96%～98.71%）。修复前最近 8 轮为 2.41%。各轮仍保留约 8 万输入 Token，9 轮无 API 报错、无缺失 usage；不含图片识别等独立任务。这里只验证了短时间连续聊天，长时间闲置与前缀变更后的表现仍需观察。原始统计仅存本机 `runtime/qa/cache-prefix-real-followup.json`，不发布聊天内容或账号。

自动召回使用本地向量与长记忆分块最大相似度、词项、重要性、距用户提及时间联合排序。普通候选须有词项或足够的语义相关性，稳定的高重要性核心事实可以常驻；不会因还有预算就把低分候选填进去。具体分数是初始校准值，不声称适配所有聊天。原始记录检索先对整个人的历史按匹配度排序，再限量返回，避免 120 条近期泛泛匹配遮住更早的准确原话；超长原文返回带源偏移的相关节选。

数据库的聊天、记忆、向量分块、摘要版本没有按 Token 设置容量上限，仅受磁盘容量和维护能力约束。常驻注入、历史检索、近期原文、摘要和最终模型窗口分别计数。保存全部数据不等于模型能同时看到全部历史，也不保证每次都准确想起；原文检索是压缩后的补救路径。
